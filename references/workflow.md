# 可选层：工作流与步骤改进

仅在用户明确启用工作流模式后读取。基础项目管理与经验改进始终有效；本模块不创建常驻服务或自行扩大目标。

## 1. 用交付定义步骤

先明确最终交付、使用者与验收方式，再提出能独立验收的步骤划分供用户确认。
每步都产生一个可检查的新交付；点击、搜索、打开文件等操作通常不是步骤。
探索性工作可保留开放环节；允许分支、返工、合并或取消步骤，不强行套线性流水线。

在项目内维护一份 WORKFLOW.md：最终交付、步骤 ID、输入、交付物、验收依据、依赖、对应 Skill 路径与版本、审核安排。
状态文件仅保存模式、该文件入口和当前进展，不复制整张流程表。
边界不清时先试行小段流程；确认前不批量生成空 Skill。

## 2. 为每步建立可复用 Skill

按确认的划分，在项目内创建步骤 Skill；沿用已有目录习惯，否则可用 workflows/<流程名>/steps/<步骤名>/SKILL.md。
每份有 name、description 前置元数据，说明何时使用，并包含：

- 输入与缺失信息的处理方式；输入来自哪份已验收交付。
- 本步交付与验收依据，如何交接给下一步。
- 方法、判断依据、必要工具和适用边界；内部解法可以变化。
- 本步骤反馈与验证案例的相对路径，按需读取。

交付约定相对稳定，方法可以演进；不是把全部操作写死。
步骤独立调用时也应能理解本步要求，不依赖某次聊天。
项目局部有效的改进留在项目内，不自动修改全局安装的 Skill。

## 3. 执行、验收与续接

每次运行关联运行 ID、步骤 ID、Skill 版本、输入版本、交付位置和验收状态。
区分待审核、需修改、人工通过、按已批准规则检查通过；AI 自评不能冒充人工通过。
按已约定的审核安排交接：若需要人工审核，未通过就不把产物当成已批准输入。
返工保留上一份交付与反馈；上游交付变化时，标记受影响的下游结果待复核。
中断后从记录核对实际产物与未完成步骤，不凭聊天摘要重复生成或宣告完成。
最终完成以最终交付的验收为准，不以全部步骤运行过为准。

## 4. 人工反馈归到具体步骤

每次人工筛选、否决、修正或接受，都在对应步骤的 FEEDBACK.md 或已有等价记录中保存：

| 字段 | 内容 |
|---|---|
| 对象 | 运行、步骤、Skill 版本、交付版本或位置 |
| 人工处理 | 接受、否决、选中哪个候选、修改前后差异 |
| 理由与来源 | 用户明确说明；没有说明就写未知，AI 解释单列为假设 |
| 适用范围 | 本次特例、特定受众偏好或可能通用，不能混写 |
| 后续 | 待分析、已关联提案、已验证、未采纳 |

反馈与 Skill 正文分开；不把每次修改自动追加成永久规则。
下游发现的错误要追溯输入和责任步骤；归因不确定时保留假设，不把问题直接算给发现它的步骤。
跨步骤反馈使用同一个反馈 ID 和引用，避免重复维护。
只保存完成复盘所需的信息，去除凭据与私人数据；不复制整段聊天。

## 5. 按需提出方案，批准后更新

日常执行只收集反馈，不主动展开整轮优化。工作者要求“复盘 / 提出改进方案”时，再分析有关记录。
提案至少说明：关联反馈、可能原因、具体修改、适用范围、风险、验证案例和撤回条件。
可以建议不改 Skill、改善输入或调整步骤划分；不能把所有问题归因于提示词。
证据不足的提案明确标为假设，不以反馈次数代替判断。

提出方案不等于获准修改。工作者批准具体方案后：

1. 保留旧版本，按批准范围准备候选版本；不影响正在执行的旧版本任务。
2. 用原失败例、相近但不同的案例、原本通过的案例检查候选版本。
3. 记录方法、环境、案例和结果。未实际运行就标待验证，不把文字走查写成实测。
4. 验证符合批准的采用条件后更新生效版本和引用；失败则保留旧版、记录原因，不无限自改自测。

一次通过不能证明普遍可靠。降低人工审核强度需要工作者另行决定适用范围、证据与恢复审核条件；启用本模式不包含这项授权。

## 6. 控制体积与退出

步骤 Skill 只保留已采用的方法与有效经验；原始反馈归档后仍可追溯，按任务检索。
只创建实际需要的文件；反馈少时不建立额外的提案库或管理系统。
流程改动与步骤方法改动分开记录；用户停用时停止本模块，基础管理继续。
多轮未改善时报告证据和局限，提供换方法、简化流程或接受局限的选项，不擅自扩建 Agent。
